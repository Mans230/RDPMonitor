# Clean onboarding - 0.8.0

The approved coss onboarding source is translated into three native pages: Welcome, Google sign-in and Add server. The welcome server/network artwork and official multicolor Google mark use the supplied exact vector paths. The saved neutral theme, Inter, gutters, headline styles, frame/panel fields and bottom actions follow the reference with native safe-area and keyboard accommodation. Connected coss sections and bottom glass navigation are unchanged.

Get started changes only the page. Continue with Google invokes the existing nonce-bound Google identity provider and validates the returned identity before opening Add server. Provider cancellation/failure stays on sign-in. Android Back cancels an in-flight auth job; generation and cancellation guards reject late results. Reauthentication of the same workspace preserves server sessions. Changing account retains the existing namespace isolation and clears the old app sessions before changing owner. Existing Google workspace profiles are preserved. Legacy private-namespace data is not deleted or silently copied into another identity.

First-time fields start empty. Returning profiles are chosen through Saved servers, without signing out of an active monitor. The form validates name and the existing private HTTPS .ts.net boundary before any connection attempt. Default new connections remain monitoring-only. Administration escalation still comes from the existing reviewed management path; pending approval shows its requested scope, code comparison and browser action. Back/sign-out clears abandoned pairing attempts. No Google login, button tap or successful address validation grants server privileges.

The visible offline demo and private-workspace bypass entries, sample cards and explanatory setup paragraphs were removed from production onboarding/connection pages. Automated tests and internal fixtures remain. Concise failures, saved-server selection, account controls and essential Passkey/owner approval are retained. No token is shown in chat or logs.

Verification uses native journeys with an injected credential-provider boundary and local connection callback capture only: three pages/back navigation, provider cancellation and late results, returning accounts/profile selection, form rejection before networking, approval code/scope visibility, and 320/390/768dp screenshots in both themes. Internal fixture monitor journeys continue to cover all post-login functions. Physical Google account selection, biometric prompts, actual Tailscale connectivity, keyboard/device GPU behavior are separate device acceptance checks.
